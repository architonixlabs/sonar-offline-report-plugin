# SonarQube Offline Report Plugin v2.0.1

Status: enterprise-candidate prerelease for controlled evaluation. It is
published only by the clean-tag workflow; the earlier dirty-source Linux lab
candidate and the unpublished v2.0.0 tag are not release assets.

Version 2.0.1 is the first publishable Model v3 reporting and runtime-hardening candidate. The v2.0.0 tag produced no GitHub release or assets because its workflow stopped safely at SBOM-specific attestation. v2.0.1 adds a deterministic CycloneDX serial bound to repository, tag and source commit; the report model and output contracts are otherwise unchanged.

This is not an enterprise-GA declaration: authenticated SonarQube authorization, representative target-server load, persona-owner acceptance, desktop Office/accessibility and security/privacy review remain promotion gates. The Model v3 Linux Docker upgrade and rollback rehearsal pass; the exact published v2.0.1 artifact is qualified separately after publication.

The candidate targets SonarQube Community Build `26.6.0.123539` and Plugin API `13.7.0.4381`. Other server/API versions are unsupported until they appear in the qualified compatibility matrix.

The major-version contract remains intentional: generated JSON uses Report Model v3, portfolio artifacts add a machine-readable contract, and CSV is a manifest envelope. Automated consumers must validate and migrate to the new schemas. Saved report templates remain backward compatible with template schemas 1 and 2.

## Highlights

- Adds Report Model v3 portfolio reporting for up to 50 visible projects, with bounded concurrency and independent project outcomes.
- Reuses one frozen collection snapshot and report ID across HTML, XLSX, DOCX, print, CSV and JSON exports.
- Separates `collectedAt`/`collectionCompletedAt` from artifact `exportedAt`, format and completeness metadata.
- Uses credentialed same-origin Fetch with real abort propagation and retains a compatibility request fallback.
- Adds explicit portfolio preflight limits: 25,000 requested issues and 50,000 components in total; DOCX registers are limited to 2,000 selected issues.
- Adds test-execution, coverage-denominator and per-file measure evidence without collecting source code.
- Publishes a CycloneDX SBOM, SHA-256 checksums, validation evidence and GitHub artifact/SBOM attestations.

## Integrity and provenance

The release workflow serializes the tag, verifies its commit is reachable from the default branch and agrees with Maven/npm declarations, removes checkout credentials before running build code, rebuilds and tests the browser bundles, runs Maven verification, reruns the real-browser persona suite and bounded maximum export benchmark on the clean release inputs, and revalidates the remote tag before attestation and publication. Repository-wide `refs/tags/v*` update/deletion protection remains an administrator-owned promotion control.

The workflow publishes:

- `sonar-offline-report-plugin-2.0.1.jar`
- `sonar-offline-report-plugin-2.0.1.jar.sha256`
- `sonar-offline-report-plugin-2.0.1.cdx.json`
- `sonar-offline-report-plugin-2.0.1.cdx.json.sha256`
- `sonar-offline-report-plugin-2.0.1.provenance.json`
- `sonar-offline-report-plugin-2.0.1.provenance.json.sha256`
- `sonar-offline-report-plugin-2.0.1.validation.tar.gz`
- `sonar-offline-report-plugin-2.0.1.validation.tar.gz.sha256`

GitHub artifact attestations bind every published file to the repository workflow and source revision. A separate SBOM attestation binds the finalized CycloneDX document to the JAR. Its deterministic RFC 4122 UUID v5 serial is derived from repository, tag and immutable source revision before the provenance manifest and checksums are created.

The provenance manifest binds the JAR, SBOM and run-specific validation archive; that archive retains browser evidence, deterministic screenshots/print PDFs and benchmark assertions from the clean release inputs, with normalized archive metadata. The release build stamps the verified revision and a deterministic, path-framed `plugin-build-inputs-v1` digest of the actual build inputs into both browser bundles. The report-level `artifactDigest` remains explicitly `null`/`not_computed` because final downloaded browser bytes are not cryptographically hashed in this release.

## Deployment and rollback

1. Back up the current plugin JAR and record the SonarQube version, edition and current plugin inventory.
2. Verify the downloaded checksums and GitHub attestations before copying the JAR into the SonarQube extensions directory.
3. Remove the older offline-report JAR so only one plugin version is present, then restart SonarQube.
4. Confirm the project and portfolio pages load, generate a small complete report, exercise cancellation, and inspect SonarQube logs.
5. To roll back, stop SonarQube, restore the previous JAR, remove the 2.0.1 JAR and restart. The plugin has no database migration or persistent server-side report data.

## Promotion gates

Do not promote this candidate to broad production or enterprise GA until the supported SonarQube matrix has authenticated ordinary-user and negative-permission evidence (including a non-root context path), representative 25,000-issue/50,000-component portfolios have passed target-server load observation, all target personas have signed off each applicable format, and security/privacy, Office and accessibility review is complete. The deployment and rollback operating model has been rehearsed; see [deployment validation](../DEPLOYMENT-VALIDATION-2026-08-22.md).
