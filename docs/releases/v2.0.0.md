# SonarQube Offline Report Plugin v2.0.0

Status: enterprise-candidate prerelease for controlled evaluation. It is
published only by the clean-tag workflow; the earlier dirty-source Linux lab
candidate is deployment evidence and is not a release asset.

Version 2.0.0 is an enterprise-candidate reporting and runtime hardening release for controlled pilot evaluation. It is not an enterprise-GA declaration: authenticated SonarQube authorization, representative target-server load, persona owner acceptance, desktop Office/accessibility and security/privacy review remain promotion gates. The exact-candidate Linux Docker upgrade and rollback rehearsal pass.

The candidate targets SonarQube Community Build `26.6.0.123539` and Plugin API `13.7.0.4381`. Other server/API versions are unsupported until they appear in the qualified compatibility matrix.

The major version is intentional: generated JSON advances from Report Model v2 to Model v3, portfolio artifacts add a new machine-readable contract, and CSV becomes a manifest envelope. Automated consumers must validate and migrate to the new schemas. Saved report templates remain backward compatible with template schemas 1 and 2.

## Highlights

- Adds Report Model v3 portfolio reporting for up to 50 visible projects, with bounded concurrency and independent project outcomes.
- Reuses one frozen collection snapshot and report ID across HTML, XLSX, DOCX, print, CSV and JSON exports.
- Separates `collectedAt`/`collectionCompletedAt` from artifact `exportedAt`, format and completeness metadata.
- Uses credentialed same-origin Fetch with real abort propagation and retains a compatibility request fallback.
- Adds explicit portfolio preflight limits: 25,000 requested issues and 50,000 components in total; DOCX registers are limited to 2,000 selected issues.
- Adds test-execution, coverage-denominator and per-file measure evidence without collecting source code.
- Publishes CycloneDX SBOMs, SHA-256 checksums and GitHub build-provenance attestations with the release assets.

## Integrity and provenance

The release workflow serializes the tag, verifies its commit is reachable from the default branch and agrees with Maven/npm declarations, removes checkout credentials before running build code, rebuilds and tests the browser bundles, runs Maven verification, reruns the real-browser persona suite and bounded maximum export benchmark on the clean release inputs, and revalidates the remote tag before attestation and publication. Repository-wide `refs/tags/v*` update/deletion protection remains an administrator-owned promotion control. The workflow publishes:

- `sonar-offline-report-plugin-2.0.0.jar`
- `sonar-offline-report-plugin-2.0.0.jar.sha256`
- `sonar-offline-report-plugin-2.0.0.cdx.json`
- `sonar-offline-report-plugin-2.0.0.cdx.json.sha256`
- `sonar-offline-report-plugin-2.0.0.provenance.json`
- `sonar-offline-report-plugin-2.0.0.provenance.json.sha256`
- `sonar-offline-report-plugin-2.0.0.validation.tar.gz`
- `sonar-offline-report-plugin-2.0.0.validation.tar.gz.sha256`

`collectedAt` and `collectionCompletedAt` identify the frozen collection snapshot. Each exported artifact has its own `exportedAt`; `generatedAt` remains only a backward-compatible alias for collection completion on an unexported snapshot and for `exportedAt` on an artifact clone. Report ID and collection timestamps do not change when another format is created from prepared data.

GitHub artifact attestations bind every published file to the repository workflow and source revision, and a separate SBOM attestation binds the CycloneDX document to the JAR. The provenance manifest binds the JAR, SBOM and run-specific validation archive; that archive retains browser evidence, deterministic screenshots/print PDFs and benchmark assertions from the clean release inputs, with normalized archive metadata. The release build stamps the verified revision and a deterministic, path-framed `plugin-build-inputs-v1` digest of the actual build inputs into both browser bundles. The report-level `artifactDigest` remains explicitly `null`/`not_computed` because final downloaded browser bytes are not cryptographically hashed in this release.

Custom reproducible builds can supply `OFFLINE_REPORT_SOURCE_REVISION=<hex>` and `OFFLINE_REPORT_SOURCE_DIGEST=sha256:<hex>` when generating browser bundles. These values are validation inputs, not unchecked overrides: the revision must match Git when Git is available, and the digest must match the bytes computed from the declared `plugin-build-inputs-v1` scope. They identify source/build inputs; they are not a digest of the later browser download.

## Deployment and rollback

1. Back up the current plugin JAR and record the SonarQube version, edition and current plugin inventory.
2. Verify the downloaded checksums and GitHub attestation before copying the JAR into the SonarQube extensions directory.
3. Remove the older offline-report JAR so only one plugin version is present, then restart SonarQube.
4. Confirm the project and portfolio pages load, generate a small complete report, exercise cancellation, and inspect SonarQube logs.
5. To roll back, stop SonarQube, restore the previous JAR, remove the 2.0.0 JAR and restart. The plugin has no database migration or persistent server-side report data.

## Promotion gates

Do not promote this candidate to broad production or enterprise GA until the supported SonarQube matrix has authenticated ordinary-user and negative-permission evidence (including a non-root context path), representative 25,000-issue/50,000-component portfolios have passed target-server load observation, all target personas have signed off each applicable format, and security/privacy, Office and accessibility review is complete. The deployment and rollback portion has been rehearsed in the target Docker/Linux operating model; see [deployment validation](../DEPLOYMENT-VALIDATION-2026-08-22.md).
